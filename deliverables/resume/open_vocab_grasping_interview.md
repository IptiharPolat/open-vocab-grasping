# 开放词汇感知驱动的机械臂抓取规划：面试材料

## 100 字以内项目简介

PyBullet仿真抓取：YOLO-World检测文本目标，RGB-D重建点云，官方GraspNet生成6-DoF候选，经语义、碰撞和IK筛选后抬升；DeepSeek仅输出安全校验的结构化计划。

## 60 秒口述

这个项目解决的是“用户说抓哪个物体，机械臂如何可靠地抓起来”的问题，但当前只在 PyBullet 仿真中验证。输入中文或英文指令后，DeepSeek 只负责把任务解析成受约束的 JSON 计划；YOLO-World 用动态文本类别在 RGB 图中检测目标，RGB-D 再重建为米制点云。随后我用隔离环境中的官方 GraspNet 生成场景级 6-DoF 平行夹爪候选，并通过检测框投影、深度一致性、桌面和点云碰撞、工作空间、接触支持、IK 与轨迹插值逐层筛选，最后控制 Franka Panda 完成预抓取、接近、闭合和抬升。正式评估覆盖四类物体、40 个固定 seed，检测为 38/40，目标选择 37/40，IK 可达 35/40，端到端成功 26/40。DeepSeek 的 40 个结构化计划都通过校验，但物理完整系统仍是 26/40，这说明主要瓶颈在感知、候选筛选和接触稳定性，而不是语言解析。

## 面试官可能追问的 8 个问题

1. **如何避免仿真真值泄漏到开放词汇感知？**

   开放词汇路径只使用 RGB-D、相机标定和 YOLO-World 检测；实例 ID 只用于 oracle 上界、检测 IoU 评估、物理碰撞查询和最终成功判定，不能作为语义选择输入。

2. **为什么二维检测框还需要深度一致性？**

   一个框可能同时包含桌面、背景或邻近物体。候选中心除投影到框内，还要与框内稳健深度参考一致，随后再结合目标点云、非目标点云间隙和接触支持降低误关联。

3. **RGB-D 到 Panda 工具坐标系的关键难点是什么？**

   统一采用 OpenCV 光学坐标与 `T_destination_source` 命名；先从 OpenGL 深度恢复米制 z，再做相机到世界/基座变换，并将 GraspNet 的 approach/closing/height 轴适配为 Panda TCP 轴，避免未经解释的轴交换。

4. **为什么把 GraspNet 放在独立环境？**

   官方基线依赖旧版 PyTorch/CUDA 和 PointNet2/KNN 自定义扩展。通过 NPZ 请求/响应边界隔离在 `ovg-graspnet-cu117` 中，主环境的 PyBullet、YOLO-World 与评估不会被其依赖破坏。

5. **候选为什么会被拒绝？**

   筛选顺序包括语义框/深度关联、官方碰撞标记、抓取分数和宽度、桌面/工作空间、接触支持、点云间隙、预抓取与抓取 IK，以及两段关节插值轨迹。每个候选都保留拒绝原因。

6. **DeepSeek 是否直接控制机器人或执行任意代码？**

   不会。模型只返回 JSON 计划；系统校验 Schema、目标白名单和六步顺序后，才本地生成固定 DSL。AST 验证拒绝导入、内置函数、额外调用、顺序变化和目标变化；`SafeRobotController` 让每一步与真实流水线同步。

7. **为什么 40/40 计划正确，但抓取只有 26/40？**

   计划层回答“抓哪个”，而物理层还要处理检测漏检、候选全部被安全过滤、以及闭合后接触不稳定。40 回合中有 1 次检测失败、4 次无接受候选、9 次未成功抬升。

8. **下一步如何迁移到真实系统？**

   替换 PyBullet 相机为标定后的真实 RGB-D 输入，重新估计相机到机器人基座外参；接入真实机器人控制与安全停机；增加力/接触反馈、真实碰撞模型、域随机化和独立测试场景。现有结果不能直接视为真机性能。
